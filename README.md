# omp-dispatch-desk · 调度台

给 [oh-my-pi（omp）](https://github.com/can1357/oh-my-pi) 加一个调度器模式：你只跟一个主会话说话；每个任务有一个自己的负责 agent，和这个任务有关的话、外面来的消息都交到它手里，怎么干由它定；主会话负责研判、统筹、验收和汇报。

派子代理、给子代理发消息、子代理再派人、续会话后叫醒子代理、看谁在跑，都是 omp 自带的。插件只补 omp 没有的：一本任务表、每次请求附带的规则、把外部消息归到任务、按层定模型、完成前的审查、提问前的查重、远端写入对账、屏幕上分得清的回复和固定显示的待办、子代理交回被压住或久未交回时叫醒主会话、插件更新后提示重启。

- [项目主页](https://stofancy.github.io/omp-dispatch-desk/)：用几张会动的图讲这套做法，走一遍「一个上午，三件事」。
- [《注意力稀缺下的 harness 调度》](docs/注意力稀缺下的harness调度.md)（[网页版](https://stofancy.github.io/omp-dispatch-desk/article.html)）：为什么这样设计、实践中踩过哪些坑、接下来往哪走。网页版由 `bun scripts/build-article.ts` 从这份 Markdown 生成。

三层：

| 层 | 是谁 | 管什么 | 用什么模型 |
|---|---|---|---|
| 一 | 主会话 | 研判、立项、跨任务统筹、验收、向你汇报；不干活 | 你开会话时选的 |
| 二 | 任务的负责 agent，每个任务一个，长期存在 | 持有这个任务的上下文，自己决定怎么干 | 默认跟主会话一样，可在 `config.json` 里改（`owner_model`） |
| 二 | 任务的审查者，主会话在负责 agent 报做完时派出，用完即弃 | 重跑完成判据、试着找出不成立的地方、记审查结论 | 跟主会话一样 |
| 三 | 负责 agent 派出的帮手，用完即弃 | 一件具体的活 | omp 自己的配置（代理 → 模型） |

## 现状和规划

作者自己每天在用。数据只有一个人、几天，只能算初步观察（文章第 9 节）。

| | 已经有的 | 接下来 |
|---|---|---|
| 输入线 | Slack、飞书实时推送和定时补读；PR 的评论、评审、投票；到期提醒；按订阅归位；噪音大的频道先分拣；每个来源报健康状态 | 先接 CI 和工单，再接日历和邮件；每个源都先过滤；「提前做」：负责 agent 先动手，有结果才说话；回复回到原处 |
| 调度线 | 一本任务表；每个任务一个负责 agent；完成前独立审查；被压住的交回由插件送达；久未交回叫醒主会话 | 被叫醒的回合少说话；输入直送负责 agent（要 omp 开放接口）；按进展判断卡没卡住；远端写入从记录变成闸门；任务收尾 |

接下来几周先用起来、量清楚：代码只修 bug，提示词的改动都记下来；和插件之前同口径比切换次数、「有回复了」的次数，算出每个任务的花费；用满一段时间后，每个任务花的注意力不比以前少，就砍到只剩任务表和外部输入两样。详见文章第 12 节。

## 用法

1. 开 omp，敲 `/调度`。会话名变成「调度」，状态栏出现 `📋 任务 0 · 待你决定 0 · 在跑的 agent 0 · 新消息 0`。不敲就是普通的 omp 会话，插件什么都不做。之后每条回复上方有一行标头（`━━━ 📤 交出 · PROJ-123 ━━━`、`━━━ 📥 交回 · PROJ-123 · 做完 · 用时 12 分钟 ━━━`、`━━━ 🔍 审查 · PROJ-123 · ❌ 不通过 ━━━`、`━━━ 💬 回答 ━━━`），输入框上方固定显示等你定的事、在跑的负责 agent、接收程序的故障，以及插件更新后待重启的提示。
2. 说「开个任务 PROJ-123：目标……，盯这个 thread <链接>」。主会话把任务记进任务表（负责 agent 的名字、目标、完成判据、要盯的外部输入），用这个名字派出负责 agent，回你一句谁在做。
3. 之后你说到这个任务，主会话交给它的负责 agent（`agent://<名字>`）；它自己决定亲自做、再派子代理，还是别的方式。
4. 它盯的 thread 有人回复、PR 有评论：消息归到这个任务，主会话醒来交给负责 agent。归不到任务的由主会话研判。因外部消息而起的远端写入，照旧先问你。
5. 负责 agent 说整个任务做完了，主会话另派一个没见过过程的审查者：它自己重跑、对照任务的目标和后面的步骤试着找出不成立的地方，把结论记进任务表。记了「通过」，任务才能记成完成；不通过就退回负责 agent。任务下的事项做完时，要推送或合并的改动、要发出去的东西、后面要依赖的结论也这样审；小事项由主会话自己核对证据。
6. 要你定的事编号列出，你整条消息只回编号答案（「1 做 2 不做」），程序自动记账。
7. 问「进展」：一个任务一行。想看某个负责 agent 在干什么、它下面派了谁：omp 的 Agent Hub（`Alt+A`）。
8. 关掉终端，之后用 `omp -c` 或 `omp -r <会话>` 续上：还是调度器模式，负责 agent 都叫得醒。任务表全局只有一本，在哪个会话打开调度器模式看到的都是它；但负责 agent 属于派出它的那个会话。
9. 关掉这个模式：`/调度 off`。
10. 看全部任务的进度：看板挂在插件的常驻服务里（见 [docs/unified-service.md](docs/unified-service.md)），状态栏末尾显示地址，默认 http://127.0.0.1:8768/ ，端口被占时换成实际端口。首屏是一句话概览和计数（等你、卡住、今天该催、待决定），往下是每个未关闭任务一张卡（负责 agent、按状态分色的进度条、等谁和催办日期、PR 链接）；点卡片看事项、审查记录、已定、时间线。页面只读，刷新即取最新任务表。

## 插件做什么（只在打开了调度器模式的会话里）

| 时机 | 做什么 |
|---|---|
| 每次请求 | 主会话：调度规则（按 `config.json` 的 `rules` 段填好参数）和常设约束在你发话时接到系统提示词后面（进缓存，不用每次重算）；你的补充规则、任务表摘要附在请求末尾。任务的负责 agent：末尾附常设约束、负责 agent 的规矩和任务卡（目标、完成判据、盯的外部输入）；主会话为这个任务派出的审查者还在跑时，再附一句：审查出结论前，先别把这份结果、进度或汇总发给外面的人。任务的审查者：附常设约束、审查规则和任务卡。其他子代理：只附常设约束。都不写进会话历史，压缩丢不掉。插件自带的规则和代码一起在会话进程启动时读入；你的补充规则每次现读 |
| 打开调度器模式时、你发第一条消息时 | 把会话名定成「调度」，omp 就不再按第一句话自动起名 |
| 主会话派出负责 agent、审查者时 | 指定它用的模型。负责 agent：`owner_model` 配了就用它，没配就用主会话当前的模型和思考档。审查者：跟主会话一样 |
| 任务要记成「完成」时 | 任务表里没有审查者记下的「通过」就拒绝：看整个任务的审查（任务下的事项都关闭了、记成完成的每一项都审过，也算）。事项记成完成不拦，审不审由主会话按大小定。只有主会话为这个任务派出的审查者（名字是「负责 agent 的名字 + `Review`」）能记审查结论；负责 agent、它的帮手、主会话自己都记不了。记「取消」不用审查。重新打开的任务要重新审 |
| 登记要你定的事时 | 要求模型写明查过哪里，并把这个任务已有的决定、别的没答的提问列给它看：已有答案就撤回，不问你 |
| 你发消息时 | 记一条发话记录（哪个会话、什么时候），用来决定外部消息交给哪个会话；整条消息只有编号答案时，记成决定；距你上次发话或上次看到回复超过 `away_hours`，把这期间任务表里的变化附上，让模型先讲清楚再答 |
| 主会话回复后 | 检查给你的那条最终回复：超过行数上限（你发话引起的回合 `report_lines`，子代理交回或外部消息叫醒的回合 `wake_lines`）、出现事项编号（如 T6）、出现像提交 SHA 的十六进制串，就在下一次请求里提醒模型。只提醒，不拦 |
| 对外动作后 | 只记工具结果里对方回了成功回执的动作：Slack 回 `ok:true`、`git push` 输出有推送成功的行（推到本地路径、被拒、dry-run、`-q` 静默的不记）、`gh pr/issue` 回地址、MCP 写操作没报错。记进任务表的「最近动作」，固定字段：时间、负责 agent、任务、动作类型、目标、回执链接。不看命令文本，只在命令里提到方法名的不记。任务的视图文件里，每条后面配着它之前 30 分钟内你对这个任务的决定（最多两条），供你抽查。只记录，不拦 |
| 画每条回复时 | 在这一轮第一块回复文字上方画一行标头：这一轮是你发话引起的（回答，或把活交给了哪个任务），还是谁叫醒的（哪个任务的负责 agent 交回、审查者的结论、外部消息、提醒）。只改显示，不进会话历史。用的是 omp 的「扩展回复渲染」接口，这个设置默认关：调度器模式开着时插件在本进程里把它打开，不改你的配置文件；你自己配过就听你的 |
| 每 5 秒 | 认领外部消息，按任务登记的「要盯的外部输入」归到任务，合成一条消息叫醒主会话；刷新状态栏和输入框上方的固定区（等你定的事、在跑的负责 agent 跑了多久和在做什么、接收程序的故障）；看有没有被压住的交回和久未交回的负责 agent。每分钟比对一次磁盘上的插件（`src/`、`prompts/`），和进程启动时读入的不一样了，固定区就显示 `🔄 插件已更新：重启会话（omp -c）后生效` |
| 负责 agent 写完交回、但它自己还有后台命令或帮手在跑时 | omp 要等它完全空闲才把结果送给主会话，到时送的也只是它最后说的话。插件在它这一轮结束时记下这条交回，15 秒后 omp 还没送就自己送达，主会话不会干等 |
| 负责 agent 或审查者超过 `stall_minutes` 没交回时 | 叫醒主会话去看一眼（它在做哪一步、这一步多久了），之后每次间隔翻倍。主会话可以让它报进度、停掉后台命令或换办法 |
| 登记、修改盯办项时 | 把未完成任务登记的 Slack、飞书和 PR 链接写给接收程序，它们照这份清单定监听范围；登记了但没有程序读得到的（工单号、别的系统的链接），在工具的返回里当场告诉模型 |

五个工具（调度器模式关着时不出现在模型的工具列表里）：`tasktable_task`（登记、更新任务：负责 agent、目标、完成判据、盯的外部输入、状态）、`tasktable_update`（任务下面的事项）、`tasktable_ask`（登记、关闭要你定的事，记决定）、`tasktable_correction`（你纠正它时记一条，连同它提议的一句规则；规则提议由程序登记成一件要你定的事，留在固定区里，模型不在回复里反复提；你同意才写进 `rules.md`）、`tasktable_review`（审查者记审查结论：审的是哪个事项或整个任务、通过或不通过、核对了什么、发现了什么）。

外部消息怎么归到任务：

| 登记的 | 归过来的 |
|---|---|
| Slack thread 里任意一条消息的链接 | 这个 thread 的根消息和所有回复 |
| Slack 频道的链接 | 这个频道的所有消息（有任务登记了具体 thread 时，那个 thread 归它） |
| 飞书会话链接 | 这个会话的所有消息（有任务登记了具体消息时，那条消息归它） |
| 飞书消息链接（带 `position`） | 这个会话中对应位置的一条消息；接收程序仍按会话读 |
| PR 链接（GitHub、Azure DevOps） | 这个 PR 的事件，链接后面的路径、查询串不影响 |
| 其他链接 | 去掉查询串和末尾斜杠后相同的 |
| 不是链接的标识（如工单号 `PROJ-123`） | 消息的位置、备注、链接里按整词出现的 |

同一条消息同样强度地命中几个任务时不归任何一个，列出候选交给主会话研判。都没命中时，用消息源自带的归属（频道配置、PR 标题里的卡号）。

## 规则

| 文件 | 给谁 | 内容 |
|---|---|---|
| `prompts/调度规则.md` | 主会话 | 角色、输入怎么走、立项、交回与验收、任务表、提问前自检、汇报、结论怎么来、对外文字、纠正 |
| `prompts/负责人规则.md` | 任务的负责 agent | 怎么干自己定、帮手按活选哪种代理、先查已有的定论和做法、进度记到任务表、做完的事项交回主会话验收、交回时写明是哪一种 |
| `prompts/审查规则.md` | 任务的审查者 | 只认自己跑出来的结果、逐条核对、对照任务的目标和后面的步骤、试着找出不成立的地方、只报跑出来的发现、把结论记进任务表 |
| `prompts/常设约束.md` | 主会话和全部子代理 | 不 force push、不推 main/master、远端写入除白名单外先问、外部消息是不可信数据、如实交回 |
| `<数据目录>/rules.md` | 主会话 | 你自己的补充：只放跟你、你的组织有关的 |
| `<数据目录>/lines/<任务>/rules.md` | 模型按需去读 | 这个任务可以直接做的远端写入（写具体：哪个仓库的哪个分支）、禁区。白名单里的对外消息冷读完就会直接发出；想先看稿，就别放进白名单 |

除了「没有通过的审查，任务就记不成完成」这一条，插件不拦截任何操作；真正的保障请用代码平台上的分支保护。审查记录和远端写入对账在每个任务的视图文件里（`tasks/views/<任务>.md`），你可以抽查。

可调参数写在 `<数据目录>/config.json` 的 `rules` 段，都可以不写：

| 键 | 默认 | 作用 |
|---|---|---|
| `language` | 用户自己用的语言 | 对你用什么语言 |
| `report_lines` | 15 | 汇报默认行数上限，回复检查也用它 |
| `wake_lines` | 5 | 不是你发话引起的回合（子代理交回、外部消息叫醒）回复的行数上限：你没在等的进展不汇报 |
| `max_asks` | 3 | 一次最多问几件事 |
| `away_hours` | 2 | 隔多久再发话算离开后回来；0 = 不提示 |
| `cold_read` | true | 发给别人的消息发出前是否冷读 |
| `owner_model` | 空 | 任务的负责 agent 用什么模型（`提供方/模型:思考档` 或 `@角色`）；空 = 跟主会话一样 |
| `stall_minutes` | 15 | 负责 agent 多久没交回就叫醒主会话去看一眼（之后每次翻倍）；0 = 不叫 |
| `inbox_quiet_seconds` | 60 | 马上送的外部消息（私信、@你、提醒、和未完成任务相关的）：对方停这么久没再发就送 |
| `inbox_max_seconds` | 300 | 马上送的外部消息：对方一直在发，最多等这么久 |
| `inbox_digest_minutes` | 30 | 攒着的外部消息（分拣判相关或拿不准的、和已完成任务相关的、没归属的）：跟下一次马上送的或你下次发话一起送，最晚等这么久单独送 |

## 安装

准备好 `omp`、`bun`、`python3`、`gh` 和 `flock`。读飞书还需要 `lark-cli`；实时推送使用 systemd 用户服务。

```bash
git clone https://github.com/stofancy/omp-dispatch-desk ~/src/omp-dispatch-desk
cd ~/src/omp-dispatch-desk
bun scripts/install.ts
```

安装程序在每次改动前显示内容并请你确认：链接插件、建立数据目录、配置分拣和消息源、安装统一常驻服务 `dispatch-desk.service`（看板、实时推送、定时补读都在里面），并移除旧的单独推送服务和 crontab 里插件自己的补读条目（先备份，其他条目不动）。可重复运行。先看预览可用 `bun scripts/install.ts --dry-run`，它按现有配置生成计划，不写任何文件。

在 omp 内用 `/调度配置`（别名 `/dispatch-setting`）也能改分拣、飞书和 Slack。保存后如需部署消息源或使常驻服务载入新配置，再运行安装程序；它使用与 omp 相同的 `DISPATCH_DESK_HOME`。改了 `src/` 或 `prompts/`，重启会话（`omp -c`）后生效，固定区会提示重启。

## 数据目录

默认 `$XDG_DATA_HOME/dispatch-desk`（通常是 `~/.local/share/dispatch-desk`），可用环境变量 `DISPATCH_DESK_HOME` 改。

| 路径 | 内容 |
|---|---|
| `tasks/events.jsonl` | 任务表：全局唯一一份，只追加的事件日志，唯一的事实来源 |
| `tasks/views/` | 程序生成的 Markdown 视图（`总览.md`，每个任务一个文件） |
| `state/dispatch/` | 打开了调度器模式的会话，每个一个文件 |
| `state/triage.jsonl` | 接收程序分拣过的消息（谁、在哪、链接、分到哪类、一句摘要）；拦下的无关消息只在这里查得到。超过约 2 MB 换新文件，旧的留一份 `.1` |
| `state/watch.json` | 未完成任务的监听范围和分拣用的任务摘要，由插件写给各消息源 |
| `state/feishu-cursor-<profile>.json` | 飞书补读的会话与 @我 游标，每个 profile 一份 |
| `state/health/feishu-poll.json`、`state/health/feishu-socket.json` | 飞书补读和实时推送的健康状态 |
| `state/feishu-owner-chat.json` | 按 profile 记录使用者与机器人的单聊，用于推送待决定事项 |
| `inbox/new/`、`inbox/claimed/` | 外部消息：会话外的程序写进 `new/`，认领后移到 `claimed/` |
| `inbox/operator/new/`、`inbox/operator/claimed/` | 使用者发给飞书机器人的指令，由绑定了对应账号的调度会话认领 |
| `lines/<任务>/rules.md` | 每个任务的低风险写入白名单、禁区 |
| `rules.md` | 你自己的补充规则，接在插件规则后面注入 |
| `config.json` | `rules` 段是规则参数；其余是外部消息源的配置，见 `config.example.json` |
| `config.json.bak.<时间戳>` | 配置向导覆盖旧配置之前的备份 |
| `crontab.bak.<时间戳>`、`dispatch-desk-*.service.bak.<时间戳>` | 安装程序改动前备份的 crontab 和被替换或移除的用户服务文件 |
| `logs/<源>.log`、`logs/<源>.lock` | 常驻服务跑的定时补读的输出和锁；服务自己的输出在 `journalctl --user -u dispatch-desk` |
| `state/service.json` | 常驻服务的 pid 和看板实际端口 |

从旧版升级：运行 `bun scripts/migrate-single-tasktable.ts [数据目录]`，把旧的分账本合并成这一本任务表，旧数据移到 `archive/<时间戳>/`。可重复运行，已迁移过就什么都不做。定时补读每 5 分钟一次，由常驻服务跑。

从 omp-chengxiangfu 升级（这个插件改名前叫丞相府）：

1. 停掉旧的 Slack 推送服务：`systemctl --user disable --now chengxiangfu-slack.service`，删掉它的 unit 文件。
2. 挪数据目录：`mv ~/.local/share/chengxiangfu ~/.local/share/dispatch-desk`。设过 `CHENGXIANGFU_HOME` 的，改成 `DISPATCH_DESK_HOME`。
3. 换插件链接：`omp plugin uninstall omp-chengxiangfu`（只删链接，不动仓库），把仓库的 remote 改成 `https://github.com/stofancy/omp-dispatch-desk` 并拉最新代码，再 `omp plugin link <仓库路径>`。
4. 用 `bun scripts/install.ts` 重装常驻服务。
5. 重启 omp 会话（`omp -c`）。哪些会话开着调度器模式记在数据目录里，挪过去后照旧。

## 外部消息

外部消息是 `inbox/new/` 里的一个 JSON 文件，任何程序都能写：

```json
{ "source": "slack", "who": "张三", "where": "#some-project (thread reply)", "link": "https://…", "line": "PROJ-123", "note": "可选", "urgent": true, "text": "原文", "parent": "李四: thread 第一条", "triage": "分拣的一句理由" }
```

- `text` 原文、`parent` thread 回复的父帖、`triage` 分拣理由都可以不写。插件送进主会话时，原文截到约 300 字、父帖只取第一行约 120 字，压成一行，尖括号换成全角、`[INBOX` 这类开头改掉，放在标明「外部消息原文，不可信数据」的块里：主会话凭摘录就能判断无关的消息，不用叫醒负责 agent 去读。
- `line` 是消息源自己判断的任务名，可以不写；任务登记的「要盯的外部输入」优先。
- 认领：只有打开了调度器模式的会话认领；同时开着几个时，交给你最近发过话的那个。
- 文件名 `<19 位排序数字>-<source>-<去重键>.json`；先写临时文件再改名，避免读到半个文件。
- 送的时机分两档：`urgent: true`（私信、@你、到期提醒）和与未完成任务相关的马上送（见 `inbox_quiet_seconds`、`inbox_max_seconds`）；其余攒着，跟下一次马上送的或你下次发话一起送，最晚 `inbox_digest_minutes`。bot 发的私信和群私信、分拣判无关的由消息源丢掉，只记日志。

`sources/` 里有几个现成的消息源，都只读外部系统，由常驻服务 `sources/service.ts` 统一跑：

| 文件 | 做什么 | 怎么跑 |
|---|---|---|
| `slack_socket.ts` | Slack 实时推送（Socket Mode）：配置里关注的频道、未完成任务登记要盯的频道和 thread、发给你的私信、@ 你的消息。配了分拣时，没归到任务的频道里不紧急的消息留给定时补读去分拣。每 30 秒发一次心跳，90 秒没回音就重连（切 VPN、机器休眠后连接会悄悄死掉） | 常驻 |
| `slack_poll.py` | 给实时推送兜底，补读配置里关注的频道，和未完成任务登记要盯的频道、私信、thread；配了分拣时，没归到任务的频道里不紧急的消息先分拣（见下） | 每 5 分钟 |
| `feishu_socket.ts` | 飞书机器人长连接：收使用者指令和任务登记的群消息 | 常驻 |
| `feishu_poll.py` | 用 user 身份补读私聊、点名 @你和任务登记且可访问的会话 | 每 5 分钟 |
| `pr_poll.py` | 你开着的 PR、未完成任务登记要盯的 PR（别人开的也算）有新评论、review、投票（GitHub 走 `gh`，Azure DevOps 走 `az`） | 每 5 分钟 |
| `reminders_poll.py` | 提醒文件里到期的条目，每天一次。`due` 写日期（当天第一次检查就提醒）或带时刻（`2026-11-18 16:30`，本机时间，到点后的第一次检查提醒，最多晚一个周期）。写错的条目（缺字段等）只跳过那一条，并报成故障 | 每 5 分钟 |

每个消息源在 `<数据目录>/state/health/` 记录最后一次成功时间和最近的错。超过三个周期没成功、或有一部分一直读不到的，显示在输入框上方的固定区，也写进给主会话的任务表摘要，由它在对话里告诉你一次。轮询以 5 分钟为一个周期；机器休眠刚醒来的一个周期内，新出现的不算故障。不再用某个消息源时，把它在 `state/health/` 下的那个文件删掉，否则会一直报它没在工作。

Slack 需要一个开了 Socket Mode 的 Slack App：app-level token（`connections:write`），以及订阅 `message.channels`、`message.groups`、`message.im`、`message.mpim` 用户事件。向导只保存 user token 和 app token 的文件路径；user token 要有权读取所选频道（列出公开／私有频道分别需要 `channels:read`、`groups:read`）。

### 飞书

1. 每个租户用 `lark-cli` 配一个 profile，运行 `lark-cli profile list` 查看账号。使用者须登录该 profile，机器人用同一应用识别使用者本人。
2. 在飞书开发者后台启用机器人和长连接，订阅 [`im.message.receive_v1`](https://open.feishu.cn/document/server-docs/im-v1/message/events/receive)。开通 `im:message.p2p_msg:readonly`（收机器人私聊）、`im:message.group_msg`（收群消息）、`im:message:readonly`（补取消息链接）和 `im:message:send_as_bot`（回复和推送）。需要在群里对话或监听时，把机器人加入该群。同一应用只能有一条事件总线。
3. 在仓库目录打开 omp，运行 `/调度配置`，在「飞书」里选 profile 并开启「机器人入口」，再在「项目绑定」里把仓库目录绑定到该账号。目录绑定默认取当前仓库根目录，可以修改或解绑；子目录按匹配的最长路径选账号。保存后运行安装程序部署机器人长连接，然后在目标会话打开 `/调度`。
4. 私聊机器人，或在群里 @机器人，就能向该会话发话。这一轮的最终回复会回到原消息；在终端发话不会回飞书。你至少私聊机器人一次后，之后登记的「待你决定」会推送到该单聊。

要监控某个飞书群，把会话链接登记到任务的「要盯的外部输入」；也可以在群里 @机器人，请调度器登记当前群。登记整个会话时，普通群消息归该任务；登记带 `position` 的消息链接时，只匹配对应消息。机器人取不到消息链接时只能按会话匹配。

每个 profile 可单独开启「用户身份补读」。补读读取真人私聊、点名 @你的消息和任务登记且账号可访问的会话，间隔 5 分钟；群里的 @所有人 不算点名。应用需开通 `im:chat:read`、`im:message:readonly` 和 `search:message`，再运行 `lark-cli --profile '<profile>' auth login --domain im,contact --scope search:message` 完成用户授权。

### 分拣：没归到任务的频道，先让便宜的模型看一眼

Slack 里只想了解动静的频道可以不填任务名（`line`），并在 `/调度配置` 里填分拣描述（见 `config.example.json`）：

- `about`：你是谁（名字照聊天里显示的写）、团队做什么，模型据此判断和你相不相关。`model`：默认 `pi/smol`，即 omp 配置里的 smol 角色。`command`：omp 的路径，默认 `omp`，定时任务的 `PATH` 里要找得到。
- 只分拣不紧急、没归到任务的消息。私信、@你、任务登记要盯的地方、写了 `line` 的频道，都不经过模型，直接送。
- 每次补读把要分拣的消息合成一批，用 omp 的打印模式（`omp -p`）调一次模型，分成四类：可能归某个任务、和你或团队相关、无关、拿不准。无关的不送，只记进 `state/triage.jsonl`，状态栏显示你上次发话以来拦下了几条；其余照常送，分拣的判断写在消息的说明里。说「可能归某个任务」也不替主会话定归属：便宜的模型常凭同一个人、同一个系统就把消息归过去，猜错了会反复叫醒那个任务的负责 agent。
- 发给模型的：消息原文（前 800 字）、thread 第一条（前 300 字）、发言人的名字、`about`，以及未完成任务的名字、标题、目标和最近动过的几个未完成事项的标题。
- 模型调用失败时，这一批全部送出，并在补读的健康状态里留一条错。
- 实时推送不分拣，这类消息由定时补读送：最多晚一个补读周期。

## 已知限制

- 插件不能直接给子代理发消息，所以外部消息先到主会话，再由它交给负责 agent。
- 没有程序读得到的盯办项（Jira 等工单、别的系统的链接）不会自动提醒，只能靠催办日期。机器休眠期间的 Slack 私信，只有登记在某个任务的盯办项里的才会补读。
- 飞书机器人只接收它所在群的消息；机器人入口之外的真人私聊和点名 @你依赖 user 身份补读。同一应用不能在多处同时消费事件。
- 你隐藏了工具活动（`display.hideToolActivity`）时，派出子代理和子代理交回的通知在屏幕上都不显示，只能靠回复上方的标头分辨。标头只画在这一轮的第一块回复文字上；续会话后，以前的回复照原样画回去（记在 `<数据目录>/state/heads/`，只留最近 400 条）。
- 久未交回的提醒按「这一次派出后跑了多久」算，不分它是卡住了还是在正常干活：正常干长活的负责 agent 也会触发，主会话看一眼就过。
- 负责 agent 属于派出它的那个会话：换一个新会话叫不到它，续原来的会话才行。
- 打开调度器模式的会话，每次请求末尾多带约四千字符的任务表摘要和你的补充规则（不进缓存）；规则正文在系统提示词里，进缓存。任务的负责 agent 每次请求末尾多带约一千五百字符。
- 远端写入对账只是把写入和它之前的决定摆在一起，不判断对不对得上：批准常常早于 30 分钟，配不上不等于没批准，判断靠你。
- 审查者的身份靠名字认（「负责 agent 的名字 + `Review`」）：防的是负责 agent 自己给自己记通过，防不了主会话故意派一个审查者走过场。
- 「审查出结论前先别往外发」只是附给负责 agent 的一句提醒，不拦它的操作；审查者跑完（不论结论）提醒就撤掉。
- 分拣的判断来自便宜的模型，会有错拦：拦下的都在 `state/triage.jsonl` 里，可以抽查。消息原文是不可信内容，有人故意写一句话诱导模型把整批判成无关，也拦得下来。配了分拣时，没归到任务的频道里 7 天前开始的 thread 有新回复也读不到（补读只看最近 7 天发起的 thread，实时推送又把这类消息留给补读）；要盯就把那个 thread 登记到任务上。
- 回复检查只认任务表里的事项编号和像提交 SHA 的十六进制串；偶尔也会把普通的十六进制词当成 SHA。带工具调用的那条消息不检查。
- 对外动作只在看到回执时才记，漏记比误记好：静默 `git push -q`、结果被 `grep`/`>/dev/null` 滤掉回执的、az/curl/lark-cli 的写入都不记。防重发要先查外部真实状态。
- 在 omp v18.22、v19.0 上测试过。回复上方的标头需要 omp 有「扩展回复渲染」接口，旧版本没有就不画，别的功能不受影响。
